Root cause (own analysis, probe = instrumented copy of profile.cpp under build-verify1-rel/probe, not committed):
  A tiny closed vector (1-4 um, about the 0.001 mm distance tolerance) offsets to a "closed" cut of ONE
  line span A->B whose ends are ~1.03 um apart (> tol, so chooseStarts' sliver filter keeps it).
  closeExactly() snaps the last line's end to its start -> a zero-length line (walk length 0, 1 span).
  With StartAt::Optimise, applyOptimisedStarts() then extracts u..u+0 -> no spans -> empty walk ->
  planLeadIns: std::stable_sort(spans.begin() + 1, spans.end()) on an empty vector = UB (segfault).
  Only Optimise reaches the empty walk: VectorStart / bbox anchors extract BEFORE closeExactly and get
  a 2-span loop P->B, A->P (cut, with an internal jump B->A along the same line) or, when the start
  projects exactly onto A (anchor BottomLeft/TopRight on v21), a 1-span zero-length walk that emits a
  plunge-only point and a misleading "lead-in left out (it would gouge a vector)" diagnostic. All
  pre-existing, identical on main. Leads off: main == branch (emit already skipped empty walks).
